# 0016 元素与 eval 的字符预算放宿主

## 问题

快照的元素清单与 `eval` 的返回值能一次吃掉整个 context。上限放哪一层，谁来算。

## 选项

1. 预算在扩展算：`page.snapshot` 收 `refsChars`，扩展按渲染后的行长度自己估。
2. 预算在宿主算：扩展只给条数，宿主在拼正文时按真实行长度裁。
3. 不设字符预算，只靠 `content` 的 32,000 字符截断兜底。

## 选了

2。两个上限进配置：`output.refsChars`（默认 8,000）、`output.evalChars`（默认 4,000）。

## 理由

一行元素最后长什么样，只有宿主的 `format/elementLine` 说了算。扩展拿不到成品长度，走选项 1 就得抄一份拼法：实测两边当前只差 9 字符，但没有任何东西拦着它漂移，改字段顺序或引号就静默不准。

选项 3 不行：32,000 是最后一道防线，不是设计预算。元素清单没有天然上限——条数上限 `maxElements` 挡不住长文本，80 个元素每个几百字符就能顶到信封线，届时截断点落在任意一行上。

裁过必须补一行 hint，写明是哪个配置裁的。静默裁剪会让模型把「只看到 40 个」读成「页面只有 40 个」，据此得出错误结论。

当年 [DEC-0006](0006-config-boundary.md) 不做 `output.fullChars`：`full` 的正文有明确上限（30,000 字符），没有可调场景。这两个不同：症状明确（一轮快照吃掉大半 context），且值随站点变化。

`eval` 只在模型可见正文截断，`details.value` 保留原值：TUI 与测试要看完整返回值，重建不了。

`chrome_cdp` 的返回值不单开配置项，复用 `output.evalChars`：两者都是模型自己要的原始数据，形态与症状一样，多一个键只是把同一个预算抄一遍。

超预算时按结构剪，不按字符切：返回值能 parse 成 JSON 就留前几项、前几个键，末尾塞一条 `… N more dropped`，预览仍是合法 JSON。直接切会给出半截 JSON，模型 parse 失败后往往再问一次，反而更贵。剪不动结构的普通长字符串才退回按字符切，并在尾巴上写清丢了多少。

## 代价

宿主多一个纯函数 `limitElements` 与一次裁剪；`page.snapshot` 的参数表不变，扩展侧不需要知道 `refsChars`。
