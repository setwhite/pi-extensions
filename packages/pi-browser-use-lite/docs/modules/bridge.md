# bridge

`src/bridge/`

## 结构

| 文件 | 内容 |
|---|---|
| `index.ts` | 门面：公开 API、发命令、转给 owner、抢端口后的本地重发 |
| `queue.ts` | 在途命令表、`/next` 的等待队列、摘取与 settle |
| `ownership.ts` | 绑端口、client 模式、探活、抢端口升为 server |
| `http.ts` | 四个端点、origin 与本地进程校验、版本闸、错误信封归一化 |

## 取舍

- 一个端口，先到者当 server：多个 pi 会话共用一个 `127.0.0.1:17318`，后到的绑不上就退成 client，把命令转发给 owner。owner 消失时 client 抢端口升为 server；并发发现时共用同一次抢占，不各抢一遍。
- 端口被别的进程占着就报错，不换端口：扩展只认一个地址，桥自己换端口等于让用户同时改两处配置。
- 命令的超时从入队算，不从投递算：没被取走的命令也要有期限，否则排队可以无限长。
- `/next` 挂起 25 秒：扩展的单次请求给 45 秒，留出的余量用于把「连接半死」与「没命令」分开。
- 版本闸挂 `/next` 的应答：扩展每次轮询都顺带看到宿主期望的版本，不用多一次请求；版本不一致时命令留在队列，等扩展换到同版本再来取。
- 扩展回的错误类别当不可信输入校验：认不出就归 `page_error`。类别决定 hint，一句没有 hint 的错落到模型手里最贵。
- 超时文案分三支：没轮询过、轮询了没取走、取走后没回结果。模型据此判断该装扩展还是该重试。
- 首次轮询宽限：`waitForFirstPoll()` 只对 `lastSeenAt === undefined` 的新桥等 2 秒（每 100ms 探一次）；见过但超过 5 分钟窗口的立即返回。首个工具调用用它，避免和扩展的 1 秒轮询抢跑。
- 时限跟着命令走：`/next` 交出去时把剩余预算减掉 500 毫秒（回传结果的余量）写进 `remainingMs`。扩展照这个数放弃，剩下的时间刚好够它把 `timeout:` 发回来，调用方拿到具体原因而不是桥的通用超时文案。
- 抢端口花掉的时间算在同一条命令的预算里：已经等掉的部分不另给一次机会。
