# 0012 两栏按内容分宽，竖线不设固定列号

> 取代 [0008](0008-fixed-left-column-width.md) 的宽度公式，沿用它的"按整题算一次"前提。

## 决定

- 左栏要的宽度 = 当前题全部左侧内容（Tab、题干原文、**所有**选项与 detail、`+ Custom…` / `→ Confirm`）按满宽排一遍后最宽的那一行。正在编辑的输入行不参与测量。
- 右栏要的宽度 = `preview` 源码最长行。
- 分宽：`room = width - 4`。右栏争空间时最多要 `floor(room / 2)`，左栏拿 `room - 右栏额度` 并按自己的内容收窄；左栏用不完时，余列归右栏。两栏各不低于 12 列，装不下就退回堆叠。
- 竖线列号 = 左栏宽 + 2，随内容移动；同一题内只算一次，滚动选项窗口与换高亮都不改。

## 为什么

[0008](0008-fixed-left-column-width.md) 的 `min(floor(width × 0.42), 54)` 是凭空拍的上限：终端一宽，左栏卡在 54 列不动，长 label 与 detail 明明有空间也被折行、截成 `…`。右栏当时也只按剩余列排版，两栏都没在按内容要空间。

反馈原话："我说的就是左栏太窄了""不要固定长度，竖线要能自适应，给左栏足够的显示空间，给右栏也有足够的显示空间"。所以宽度改由两侧内容分别提出需求，再按"争空间时对半分"分配，代码里不再有 42% / 54 / 72 这类写死的列数。

## 代价

- 竖线位置不再只由左栏决定：切到 preview 更宽的选项时右栏抢得更多，左栏随之变窄，竖线横移。同一题内左栏不变的前提也跟着变成"preview 宽度不变时才成立"。
- 两栏都装得下时右侧余列留白，宽终端上内容不会铺满整行。
- 右栏额度按 preview 源码最长行估，不含 markdown 渲染后的宽度，估算偏宽时最多浪费几列。
- 左栏更宽后单行信息量上升，超宽终端需要自己控制终端宽度才好看。
